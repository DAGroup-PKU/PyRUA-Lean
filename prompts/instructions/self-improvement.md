# Recording feedback and improving the pipeline

The input is still a real episode of a new task plus the user's goal, and the output is still reviewed batch data. This workflow turns corrections, tests, fixes and session results into feedback with provenance, then
tries general-capability improvements in an independent source snapshot. The task adapter, scene, thresholds and video prompts are task outputs generated by the agent. Commands, policy format and store layout are in
`docs/reference/capability-evolution.md`.

## Rules

- `prepare` pins the source and experience versions, and every session checks that the source has not changed. Modifying the working tree does not change a prepared task.
- The code does not read chats the host has not supplied, or private memory. The host passes visible user corrections and tool evidence through `feedback`.
- Use `user-requirement` only for exact user requirements; a guess about a cause is an `observation`. Supported kinds: user-requirement, correction, observation, code-fix, test-result, session-result, task-result.
- The host is responsible for the authenticity of the source. Writing `actor=user` in JSON does not authenticate identity. Use `source.ref` to point to the message or tool record, and put large files in `details` by path and hash.
- With no scope given, the current task scope is inherited. An explicit long-term requirement across tasks is submitted with the corresponding scope. Selectors are exact-match and ANDed; an empty scope is global.
- `supersedes` replaces an earlier requirement with the same kind and scope. The earlier record is kept. To change scope, revise the original scope and submit a new event for the new one.
- After fixing code in the working tree, capture the real diff and test log hash with `record-change`; do not write a diff by hand. It does not promote anything.

## Proposing a candidate

Work in the candidate source directory. Write `proposal.json` at the path in the message, with `event_ids`, `hypothesis`, `expected_effect`, `alternative_explanation` and optionally `lessons`. Each lesson needs `problem`, `action`,
`rationale`, `limits` and `scope`. Never treat a score reported by a model as evaluator output.

- A candidate becomes active only if it passes all checks, uses the same case denominator, regresses no declared metric and improves at least one.
- Rejections, timeouts and evaluation errors leave records.
- A candidate lesson enters active experience only after an evaluation that actually runs an agent using it. Reading the JSON is not behavioural verification.
- A real new-task evaluation starts from the episode; an existing adapter must not be the unknown-task input.
- A candidate whose parent has changed is regenerated and evaluated on the active version.

## Boundaries

- General specifications, AGENTS, standing rules, evaluation policies and the trust roots that measure candidates are outside automatic modification. A candidate cannot edit them even when the policy allows the parent directory.
- Correcting a specification or evaluator is a separate policy update with an independent comparison. The score of one optimized candidate cannot prove the scoring rules should change.
- Store locks, hashes and separate directories are not isolation against a malicious program under the same identity. With untrusted candidates, the deployment separates the evaluator, store, credentials and production output.
- A timeout bounds the local process group; it does not revoke submitted paid jobs. A retry first queries by the existing task ID and the run ledger.
- Real new-task quality and cost benefit need independent real runs; software checks and scripted fixtures do not support those claims. Report software evidence, real task results and improvement results separately.
- The runtime reads only explicit instructions and selected experience. Keep raw material, counterexamples and failures so that another person or agent can continue.
