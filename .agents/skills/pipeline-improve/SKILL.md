name: pipeline-improve
description: Convert pipeline feedback and repair evidence into scoped lessons and evaluated capability changes. Use after recurring task failures, user corrections, or a demonstrated reusable repair; task-specific adapters remain generated outputs.
---

Work through `tools/pipeline_evolve.py`; read `prompts/instructions/self-improvement.md`
for the event, proposal, driver and evaluator contracts. The host controls evaluation
and activation. Never report a proposal, a passing software fixture, or a changed
score as evidence of real robot/video quality or recursive improvement.

First identify the actual input, version, observation and current user requirement.
Distinguish a requirement from a suspected cause. Preserve scope: run, task family,
hardware and provider knowledge need not become universal rules. Use the original
event as provenance; do not invent access to previous chats.

Repair the current task where possible. For a reusable change, propose a falsifiable
cause and at least one alternative explanation, then edit only the candidate source.
Keep adapters, task prompts and task thresholds in task outputs. A generic change
can touch skills, prompts, tools and workflows together when the behavior requires it.
Add meaningful failure replay and successful/irrelevant controls; do not relax a
judge or rewrite evidence to obtain a score. Evaluator fixes follow a separate
reviewed policy revision and dual evaluation, outside the optimization patch.

Write the proposal to the path supplied by the host. Include event_ids, hypothesis,
expected_effect, alternative_explanation and optional lessons (problem, action,
rationale, limits, exact scope). Lessons remain hypotheses until an evaluation
explicitly tests their use. Read prior rejection/error evidence before retrying.
Avoid repeating the same proposal without new evidence or an explicit retry request.

In ordinary repository work, capture visible user feedback, Git changes and test
results through the event interface. Use requirement events only for actual user
requirements; observations and reflections cannot grant themselves authority.
Existing user authorization persists. Stop at the configured resource budget;
do not add an approval question for each reversible fix.

Notes and decisions are not automatically runtime instructions. Persist concise evidence and failed hypotheses
so another agent can continue. See the workflow's limits before claiming autonomy.
